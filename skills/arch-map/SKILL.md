# arch-map

레포 하나의 아키텍처를 코드에서 읽어 **호출 지도**로 그리는 스킬이다. 레포 종류를 가리지 않는다.

- **지도**: HTML 한 장이다. 왼쪽부터 사람 → 들어오는 곳 → 단위 → 바깥 시스템을 놓는다. 상자를 누르면 아래에 설명이 열린다.
- **단위**: 지도의 상자 하나가 되는 코드 묶음이다. 모듈 · 패키지 · Service 가운데 그 레포가 쓰는 것 하나로 정한다.
- **들어오는 곳**: 바깥의 요청이 처음 닿는 자리다. HTTP 경로 · CLI 명령 · 큐 소비자 · 스케줄러가 여기 든다.
- **줄**: 화살표 하나다. 코드에서 확인한 호출 하나를 뜻한다.
- **표시**: 줄 대신 부르는 상자에 붙이는 동그라미다. 여러 상자가 부르는 단위(인증 · 로깅 · 모델 호출)에 쓴다.
- **플로우**: 들어오는 곳 하나를 눌렀을 때 줄에 붙는 호출 순서 번호다.
- **스펙**: 지도 하나를 적은 JSON 이다. 상자 자리 · 호출 · 설명이 든다. 생성기가 스펙을 읽어 줄을 긋는다.

| 파일 | 하는 일 |
| --- | --- |
| [`deps.mjs`](deps.mjs) | 단위 사이 import 표를 뽑는다(분석) |
| [`gen.mjs`](gen.mjs) | 스펙 → 지도 HTML. 줄을 긋고 [`template.html`](template.html) 을 채운다 |
| [`check.mjs`](check.mjs) | 지도를 검사한다(데이터 맞춤 · 꺾인 점 겹침 0 · 줄 겹침 0) |
| [`specs/example.json`](specs/example.json) | 지어낸 작은 예(상자 16 · 호출 19 · 플로우 하나) |

셋 다 node 만 있으면 돈다(의존성 0).

다른 스킬과 나누기:

| 할 일 | 스킬 |
| --- | --- |
| 레포의 아키텍처를 분석하고 호출 지도로 그린다 | 이 스킬 |
| 설명용 그림 하나(상자 흐름 · 시퀀스 · 스윔레인)를 SVG 로 만든다 | [`svg-diagram`](../svg-diagram/SKILL.md) |
| 설계 문서 · 보고서를 HTML 한 장으로 만든다 | [`html-doc`](../html-doc/SKILL.md) |

## 1. 절차 한눈에

1. 분석한다: 들어오는 곳 · 단위 · 바깥 시스템을 찾는다(2절).
2. 호출을 코드에서 확인한다. 줄마다 근거 `파일:줄` 을 남긴다(2.3절).
3. 스펙을 쓴다: 상자 자리 · 호출 · 설명(3절).
4. `node gen.mjs <스펙.json>` 을 돌린다. 마지막 줄을 읽는다(4절).
5. `node check.mjs <지도.html>` 을 돌린다. `깨끗함` 이 나와야 한다.
6. 화면을 본다(7절).
7. 사용자가 원하면 문제를 짚는다(8절) · 플로우를 단다(5절) · Artifact 에 올린다(9절).

스펙과 지도는 그 레포의 문서 폴더에 같이 둔다(예 `docs/architecture-map/map.json` · `map.html`). 스펙이 원본이고 지도는 파생물이다.

## 2. 분석 — 코드에서 사실 읽기

지도에 그리는 것은 전부 코드에서 읽은 사실이다. 문서(README · ARCHITECTURE.md)는 낡았을 수 있으니 단서로만 쓴다.

### 2.1 뼈대 셋을 찾는다

| 찾을 것 | 어디서 읽나 |
| --- | --- |
| 들어오는 곳 | Spring `@RestController` · `@*Mapping`, Express · Fastify 의 `router.get(...)`, Next 의 `app/**/route.ts`, FastAPI 의 `@router.get`, CLI 의 명령 등록, 큐 리스너, 스케줄 표시. API 계약 파일(openapi.json)이 있으면 그 경로 목록이 원본이다 |
| 단위 | 소스 뿌리 아래 첫 폴더. 폴더 하나에 공개 창구(Service · index · `__init__`)가 하나인지 본다 |
| 바깥 시스템 | DB · 캐시 · 큐 · 다른 서비스 · 모델 API. 클라이언트를 만드는 코드와 설정 키(주소 · 접속 문자열)에서 읽는다 |

들어오는 곳이 많으면 경로 앞머리로 묶어 상자 하나로 그린다. 상자의 라벨은 실제 경로 앞머리 전체다(`/api/v1/orders`).

### 2.2 import 표를 뽑는다

```bash
node deps.mjs src/main/java/com/acme/app          # Java · Kotlin: 패키지 뿌리
node deps.mjs src --alias @/=.                    # TS · JS: 별칭 '@/x' 를 src/x 로 읽는다
node deps.mjs app                                 # Python: 패키지 폴더
```

출력은 단위마다 파일 수 · 줄 수 · 기대는 단위(import 수)다. 아래에 서로 기대는 쌍과 큰 파일 열 개가 나온다.

- 표는 "기댄다" 는 사실만 말한다. 타입만 가져다 쓰는 import 도 센다.
- 지도의 상자 후보는 이 표의 단위다. 계약 · 공용 타입 · 설정처럼 모두가 기대는 단위는 상자로 그리지 않는다.
- 서로 기대는 쌍과 방향이 거꾸로인 줄(아래층이 위층을 import)은 8절의 평가 후보다.

### 2.3 호출을 확인한다

import 표에서 후보를 뽑고, 줄을 긋기 전에 코드에서 호출을 확인한다.

- **들어오는 곳 → 단위**: 핸들러가 주입받거나 부르는 창구를 읽는다.
- **단위 → 단위**: 부르는 쪽에서 다른 단위의 창구를 쥔 필드 · 인자와 그 메서드 호출을 찾는다. 단위 안의 도구가 대신 부르는 호출도 그 단위의 호출이다.
- **단위 → 바깥**: 클라이언트 구현이 무엇에 붙는지 읽는다(HTTP · JDBC · Redis · 큐).
- 프레임워크가 대신 하는 일(권한 표시 · 트랜잭션 · 직렬화)은 호출로 세지 않는다. 세는 기준을 지도의 안내(`intro`)에 한 줄로 적는다.

확인한 호출마다 `파일:줄` 을 적어 둔다. 상자 설명의 `ref` 와 플로우 단계의 `ref` 로 들어간다. 확인하지 못한 것은 긋지 않고 보고에 "미확인" 으로 적는다.

## 3. 스펙 쓰기

[`specs/example.json`](specs/example.json) 을 복사해 고친다.

```json
{
  "title": "shop-api 아키텍처 지도",
  "titleMono": "shop-api",
  "basis": "기준 main <code>abc1234</code> · 2026-11-17 · 상자 하나가 모듈 하나 · 화살표 하나가 호출 하나",
  "intro": "호출은 다른 모듈의 공개 함수를 부르는 것만 셉니다.",
  "key": { "x": 214, "y": 500 },
  "legend": [{ "colors": ["blue"], "text": "주문 API · 주문 모듈" }],
  "badges": [{ "to": "auth", "mark": "A", "color": "blue", "text": "이 상자가 Auth 를 부릅니다" }],
  "permute": [["x-pg", "x-mail"]],
  "nodes": [
    { "id": "orders", "label": "Orders", "color": "blue", "x": 760, "y": 168, "w": 248, "h": 96, "kind": "모듈 · orders", "one": "주문 하나를 만듭니다.", "ref": "orders/Orders.kt:22-118" }
  ],
  "calls": [["orders", "auth"], ["orders", "x-db"]],
  "flows": {}
}
```

| 칸 | 뜻 |
| --- | --- |
| `title` · `titleMono` | 제목. `titleMono` 는 제목 앞머리 가운데 고정폭으로 쓸 부분(레포 이름)이다 |
| `basis` | 제목 아래 한 줄. 기준 커밋 · 날짜 · 상자와 줄의 뜻을 적는다. HTML 을 쓸 수 있다 |
| `intro` | 빈 설명 칸에 덧붙일 안내. 호출을 세는 기준을 적는다 |
| `key` | 지도 안 범례의 자리. 빈 곳의 좌표를 준다. 빼면 지도 안 범례를 그리지 않는다 |
| `legend` | 아래 설명 칸의 범례. `colors` 는 색 이름 목록이다 |
| `badges` | 표시로 그릴 단위. `to` 로 가는 호출은 줄 대신 부르는 상자의 동그라미 `mark` 가 된다. 색은 `blue · orange · green · purple · amber · red` |
| `permute` | 자리를 서로 바꿔 봐도 되는 상자 묶음(크기가 같은 것끼리, 다섯 개까지). 생성기가 다 돌려 보고 교차가 적은 쪽을 고른다 |
| `nodes` | 상자. 아래 표 |
| `calls` | 호출 `[부르는 상자, 불리는 상자]`. 같은 쌍은 한 번만 적는다 |
| `flows` | 플로우(5절) |

상자의 칸:

| 칸 | 뜻 |
| --- | --- |
| `id` · `label` | id 와 한 줄 라벨. 라벨은 한 줄로 쓴다 |
| `x` · `y` · `w` · `h` | 자리와 크기. 전부 8 의 배수다. 상자는 48 × 48 보다 크다 |
| `color` | `plain · blue · orange · green · purple · amber · red · teal · pink · olive · sky · slate · rose` |
| `frame` | `true` 면 틀이다. 테두리와 이름만 그리고 안에 다른 상자를 놓는다 |
| `entry` | `true` 면 들어오는 곳이다. 줄이 오른쪽에서만 나가고 가늘게 그린다 |
| `out` | 줄이 나갈 변을 고른다: `["right", "bottom", "left", "top"]` 가운데 |
| `small` | `true` 면 라벨을 작은 고정폭 글자로 쓴다 |
| `kind` · `title` · `mono` | 설명 칸의 머리. `title` 을 빼면 라벨을 쓴다 |
| `one` | 한 줄 설명. 꼭 쓴다 |
| `does` · `steps` · `paths` · `warn` · `ref` | 하는 일 목록 · 순서 목록 · 경로 목록 · 경고 한 줄 · 근거(`파일:줄`). HTML 을 쓸 수 있다 |
| `inner` | 안쪽 구조. `{ "cap": "머리말", "cols": [["기둥 제목", "색", "항목", …]] }`. 기둥 색은 `in · svc · graph · tool · port · out`, 뒤에 한 칸 띄고 `ol` 을 붙이면(`svc ol`) 번호 목록이다. 항목은 `이름\|설명`, 앞에 `@상자id` 와 빈칸을 붙이면(`@x-db DB`) 누를 때 그 상자로 간다 |

### 3.1 자리 잡기

자리는 손으로 정한다. 생성기는 줄만 긋는다.

1. 왼쪽부터 층을 세운다: 사람 → 들어오는 곳 → 단위 → 바깥 시스템. 호출이 왼쪽에서 오른쪽으로 흐르게 한다.
2. 들어오는 곳은 틀 하나에 세로로 쌓는다(높이 48, 간격 16).
3. 단위는 두세 열로 놓는다. 서로 많이 부르는 단위를 같은 높이나 옆 열에 둔다.
4. 바깥 시스템은 그것을 부르는 단위의 바깥쪽(오른쪽 · 아래 · 위)에 둔다.
5. 열 사이는 160 ~ 200px 로 띄운다. 줄은 16px 마다 한 줄 지나가니 176px 에 열 줄쯤 지나간다.
6. 상자의 변 하나에 닿는 줄은 16px 마다 하나다. 줄이 많이 닿는 상자는 크게 그린다.
7. 여러 상자가 부르는 단위는 `badges` 에 넣는다. 줄 여럿이 표시 여럿으로 바뀐다.

## 4. 생성기와 검사

```bash
node gen.mjs docs/architecture-map/map.json                  # → docs/architecture-map/map.html
node gen.mjs map.json --out out.html --trials 120            # 나갈 파일 · 긋는 순서를 바꿔 보는 횟수
node gen.mjs map.json --dry                                  # 그려 보고 숫자만 찍는다
node check.mjs docs/architecture-map/map.html
```

상자 서른여덟 · 호출 예순둘인 지도가 1 ~ 2 분 걸린다. 씨앗이 고정이라 같은 스펙은 늘 같은 지도가 된다.

```text
크기 1984 × 856 · 상자 16 · 호출 19 (줄 15 · 표시 4) · 꺾임 14 · 교차 6 · 점수 224 → 194 · 못 그은 호출 없음
```

| 칸 | 뜻 | 할 일 |
| --- | --- | --- |
| `못 그은 호출` | 길을 찾지 못한 호출 | `없음` 이어야 한다. 이름이 나오면 상자 사이를 넓힌다. 종료 코드가 1 이다 |
| `교차` · `꺾임` | 줄이 넘는 자리 수 · 꺾인 점 수 | 자리를 바꿨을 때 전과 견준다 |
| `점수` | 교차 × 30 + 꺾임. 앞은 처음, 뒤는 순서를 바꿔 본 뒤 | 낮을수록 좋다 |
| `스펙이 맞지 않는다` | 스펙 검사에 걸린 줄들 | 줄마다 고친다(8 의 배수 · 없는 상자 · 겹친 호출) |

`check.mjs` 는 상자마다 설명이 있는지, 줄과 플로우가 있는 상자만 가리키는지, 꺾인 점 겹침과 줄 겹침이 0 인지 본다.

## 5. 플로우 — 호출 순서 번호

들어오는 곳 하나에 호출 순서를 단다. 키는 그 상자의 id 다.

```json
"flows": {
  "e-orders": {
    "name": "POST /api/orders",
    "cap": "번호 한 줄을 누르면 지도에 그 단계의 줄만 남습니다. 같은 번호는 한 단계에서 같이 일어나는 호출입니다.",
    "more": "목록 아래에 덧붙일 글(선택)",
    "steps": [
      { "t": "API → Orders", "d": "주문 요청을 받습니다.", "ref": "orders/OrderRoutes.kt:18", "e": [["e-orders", "orders"]] },
      { "t": "API → 손님", "d": "주문 번호를 돌려줍니다.", "ref": "orders/OrderRoutes.kt:24", "e": [] }
    ]
  }
}
```

1. 핸들러에서 시작해 호출을 순서대로 따라간다. 단계마다 근거 `파일:줄` 을 적는다.
2. 단계 하나가 번호 하나다. `e` 에 그 단계의 호출을 적는다. `calls` 에 있는 호출만 적는다.
3. 한 단계에서 같이 일어나는 호출은 `e` 에 같이 넣는다. 같은 번호가 붙는다.
4. 같은 줄을 두 번 지나면 단계 둘에 같은 호출을 적는다. 번호 둘이 화살표 방향 순서로 나란히 붙는다.
5. 질문 · 입력마다 순서가 달라지는 구간(그래프 · 루프)은 한 단계로 묶는다. 설명에 "입력에 따라 고르고 되풀이합니다" 를 적는다.
6. 그 플로우에서 닿는 것을 코드로 확인한 호출만 넣는다.
7. 줄이 없는 단계(응답 보내기)는 `e: []` 로 둔다. 목록에만 나온다.

번호 자리는 지도가 줄에서 계산한다(가장 긴 토막의 가운데). 표시로 그린 호출은 표시 바로 아래에 붙는다.

## 6. 줄 긋는 규칙

생성기가 지키고 `check.mjs` 가 본다. 복잡한 선 관계를 정리하는 기법에서 가져왔다.

| 규칙 | 까닭 · 가져온 곳 |
| --- | --- |
| 화살표 하나가 호출 하나다. 확인한 호출만 긋는다 | 지도가 사실과 같아야 한다 |
| 호출마다 제 줄을 처음부터 끝까지 긋는다. 같은 곳으로 가는 줄도 합치지 않는다 | 합친 줄기는 어느 상자에서 온 줄인지 따라가기 어렵다 |
| 줄끼리는 16px 떨어진다 | 나란한 줄을 벌려 놓는 nudging(libavoid) |
| 한 점에는 꺾임 하나만 둔다. 같은 가로줄 · 세로줄의 꺾인 점끼리는 32px 넘게 띄운다 | 꺾인 점이 만나면 두 줄이 한 줄로 이어져 보인다 |
| 가로 줄이 다른 줄을 넘는 자리는 다리 모양이다 | line jump(draw.io) · edge casing |
| 여러 상자가 부르는 단위는 줄 대신 표시로 그린다. 뜻은 범례에 적는다 | motif simplification(Dunne & Shneiderman) |
| 긋는 순서와 `permute` 자리를 바꿔 가며 교차가 적은 쪽을 고른다 | 층 배치의 교차 줄이기(ELK Layered) |
| 들어오는 곳의 줄은 상자 오른쪽에서 나간다 | 읽는 방향을 하나로 둔다 |
| 상자 곁(16px)과 다른 줄 위에서는 꺾지 않는다. 틀 이름 자리는 줄이 비켜 간다 | 꺾임이 상자 · 글자에 붙으면 읽기 어렵다 |
| 테두리는 실선이다. 라벨은 한 줄이다 | 지도의 글자를 줄인다 |

걸리는 곳:

- **못 그은 호출이 나온다**: 그 호출이 지나갈 칸이 모자란다. 열 사이 간격이나 줄 사이를 16 의 배수로 넓힌다.
- **교차가 많다**: 부르는 상자와 불리는 상자를 같은 높이로 옮긴다. 바깥 상자는 `permute` 에 넣는다. 많이 불리는 단위를 `badges` 로 돌린다.
- **줄이 틀 밖으로 돈다**: 틀 안의 길이 막힌 것이다. 막은 상자 둘 사이를 넓힌다.
- **한 변에 줄이 몰린다**: 그 상자를 키우거나 `out` 으로 나가는 변을 나눈다.

## 7. 화면 보기

브라우저로 지도를 연다. 헤드리스 크롬으로 찍을 때는 이렇게 한다.

```bash
google-chrome --headless=new --no-sandbox --disable-gpu --hide-scrollbars \
  --window-size=2700,1500 --screenshot=/tmp/map.png "file://$PWD/docs/architecture-map/map.html"
```

상자를 누른 상태는 지도를 복사해 `</html>` 앞에 클릭 한 줄을 붙여 찍는다.

```html
<script>
  window.scrollBy = function () {};
  document.querySelector('.n[data-id=e-orders]').dispatchEvent(new MouseEvent('click', { bubbles: true }));
</script>
```

보는 것:

1. 평소 상태: 줄이 상자 글자와 틀 이름을 지나가지 않는다. 라벨이 상자 안에 든다.
2. 상자를 누른 상태: 나가는 줄은 주황, 들어오는 줄은 파랑으로 남고 아래 설명 칸이 열린다.
3. 플로우가 있는 상자를 누른 상태: 번호가 서로 겹치지 않는다. 목록의 한 줄을 누르면 그 단계의 줄만 남는다.
4. 어두운 테마: `<html data-theme="dark">` 로 한 번 본다.

## 8. 평가 — 적대적 검증으로 문제 짚기

사용자가 "평가해 줘 · 취약한 곳 · 이상한 부분" 을 물을 때 한다. 지도와 import 표를 놓고 반대편에 서서 본다.

보는 곳:

| 보는 것 | 찾는 법 |
| --- | --- |
| 층을 거스르는 의존 | import 표에서 아래층(공용 · 모델 호출 · 유틸)이 위층을 import 하는 줄, 서로 기대는 쌍 |
| 권한 경계 | 권한을 거는 자리(주소 규칙 · 메서드 표시)를 다 적고, 창구의 공개 메서드 가운데 검사가 없는 것을 센다. 들어오는 곳마다 검사를 지나는지 따라간다 |
| 창구를 지나치는 호출 | 들어오는 곳이 단위의 창구 대신 안쪽 도구를 바로 쥔 곳 |
| 큰 단위 · 큰 파일 | `deps.mjs` 의 줄 수와 큰 파일 목록. 한 파일이 여러 일을 하는지 읽는다 |
| 뜨거운 길의 결합 | 요청마다 지나는 길(플로우)에 운영 · 기록 단위가 끼어 있는지 |
| 상태가 사는 곳 | 저장소가 몇 종류인지(DB · 캐시 · 로컬 폴더), 여러 대로 늘릴 때 어긋나는 것 |
| 한도 | 루프 상한 · 시간 제한 · 재시도 · 요청 크기 |
| 숨은 전달 | 스레드 로컬 · 전역 상태로 넘기는 문맥이 비동기 · 풀 경계를 넘는지 |
| 지도와 코드의 어긋남 | 그린 줄에 없는 호출, 문서에만 있는 구조 |

짚은 것마다 반대 증거를 먼저 찾는다. 같은 일을 하는 다른 방어선이 있는지, 그 길에 실제로 닿는지 코드로 확인한다. 반증된 것은 "지나간 것" 으로 옮긴다.

보고 양식:

```text
문제 N — 한 줄 제목 [심각도: 높음 | 중간 | 낮음]
  사실: 무엇이 어떻게 되어 있나 (파일:줄)
  곤란: 누가 어떤 상황에서 무엇 때문에 곤란한가
  반증 시도: 무엇을 확인했고 왜 남았나
  고치는 방향: 한 줄

지나간 것: 의심했지만 코드로 반증된 항목과 그 근거
미확인: 코드만으로 확인하지 못한 항목
먼저 할 순서: 문제 번호를 심각도와 고치는 값으로 줄 세운 것
```

결함은 "버그" 라고 부른다. 코드를 고치는 일은 사용자가 지시한 뒤에 한다.

## 9. 올리기

지도는 혼자 열리는 문서 한 장이다(바깥 요청 0, 웹 글꼴 없음). 레포에 스펙과 같이 커밋한다.

Artifact 에 올릴 때는 `--artifact` 로 따로 쓴다. 문서 머리를 걷고 IBM Plex 글꼴 줄을 넣은 판이 나온다.

```bash
node gen.mjs docs/architecture-map/map.json --artifact --out /tmp/map-artifact.html
```

그 파일을 Artifact 도구로 올린다. 있던 지도를 고칠 때는 그 주소를 `url` 로 준다.

## 10. 글 규칙

- 지도의 글은 "~합니다" 로 쓴다. 한 문장에 서술어 하나를 둔다.
- 하는 것만 적는다: "추천 질문은 `recommend_question` 이 만듭니다".
- 같은 대상은 한 이름으로 부른다. 처음 나올 때 뜻을 적는다.
- 순서가 있는 호출 길은 "플로우" 라고 부른다.

## 11. 실제 예

fdc-agent-be 의 지도가 이 방법으로 만든 것이다: BE 레포 `docs/architecture-map/`(상자 38 · 호출 58 · `/api/fdc/v1/chat` 플로우).
그 레포는 이 생성기에서 갈라 낸 전용 생성기 `gen.js` 를 쓴다. API 상자를 계약(openapi.json)에서 채우고 Runner 그래프 칸을 따로 그린다.
지도에 그 레포만의 칸이 필요하면 `gen.mjs` 와 `template.html` 을 그 레포로 복사해 고친다.
